# PLAN 0.1.0 — Google sign-in and per-user MongoDB storage

## Goal and status

One plan covers real Google sign-in and private storage of each user's boards,
subjects, and tasks in MongoDB, including the API connecting them.

- Platforms: **Windows and Android**.
- Initial environment: **API on the user's computer; MongoDB Atlas in the cloud**.
  Public hosting, domains, paid subscriptions, and store distribution are excluded.
- Explicitly authorized by the user. Automated and real-device tests completed,
  including two own Google accounts on both platforms.
- Agreed baseline: `0.0.1`; target: **`0.1.0` minor**, unpublished until merge/tag.
- Before `1.0.0`, features increment minor and fixes increment patch. No major
  increment until the user explicitly decides the app is ready for `1.0.0`.
  Normal version increments apply after that milestone.
- The approval hash records the originally approved document; later translation,
  naming, and progress updates preserve the approved functional decisions.

## Starting point and architecture

The Flutter app has Windows/Android targets, Provider, Hive, and generated
adapters. Authentication was simulated. Shared Hive boxes had no account owner;
legacy data may use `default-board`, missing `boardId`, and text `subject`.
Android package: `com.microplanner.microplanner`. Both build types currently use
the debug certificate. Existing initialization work and the user's `*.env` ignore
rule were reviewed and preserved without silently including unrelated changes.

`Flutter (Windows / Android) → authenticated API → MongoDB Atlas`.

Google establishes identity. The API verifies it, retrieves/creates an internal
account, and issues expiring, revocable microplanner sessions. Only the API
connects to MongoDB. Flutter receives public API URLs and OAuth client IDs;
private database and OAuth credentials never ship with the app.

- API in `server/`: Node.js, TypeScript, HTTP/JSON, official MongoDB driver.
- Direct Google authentication, without Firebase; identity scopes only:
  `openid`, `email`, `profile`.
- Android: official `google_sign_in`, Android package/certificate registration,
  and a Web OAuth client as `serverClientId` and token audience.
- Windows: system browser, authorization code, PKCE S256, state, nonce, Desktop
  client, and ephemeral `127.0.0.1` loopback callback. The official plugin does
  not declare Windows support.
- Platform secure storage for sessions, encrypted account-specific Hive caches,
  and MongoDB as the remote source of truth. No offline write queue or live push.

## B01 — Google sign-in and sign-out

### Behavior, scope, and dependencies

Replace simulated access on both platforms. Sign-in opens the authenticated
workspace; sign-out clears visible account data and returns to login. Handle
startup, restoration, cancellation, errors, active identity, and logout; prevent
overlapping sign-in attempts. B03 supplies the API and external configuration.

The API verifies signature, issuer, configured audience, expiry, verified email,
and nonce where applicable through Google's official library. Unverified client
emails/IDs never establish identity. Google's verified `sub` identifies the
account; the profile contains name, email, and optional photo.

Restore valid sessions and reject expired/revoked ones. Revoke on logout as well
as clearing the client. Windows validates callbacks and closes its listener on
completion/cancellation. Remove mock text and require sign-in for cloud data.
Custom passwords, other providers, roles, invitations, shared boards, and account
deletion are outside scope.

### Acceptance criteria

1. Real Google access works on Windows/Android; failure/cancellation is recoverable.
2. The same Google account maps to the same internal user on both platforms.
3. Forged, expired, or incorrectly addressed tokens are rejected.
4. Restart restores a valid session; invalid sessions cannot open account data.
5. Switching accounts clears prior data, dialogs, and late responses.

## B02 — Private per-user MongoDB data

### Behavior and scope

Persist boards/order, subjects, and tasks. The same account retrieves confirmed
data on another device; other accounts have independent workspaces. Depends on
B01 identity and B03 connectivity.

- One technical database user serves the API; application users are records,
  not individual MongoDB database users.
- Server-assigned `ownerId` on domain entities. Scope every read, write, delete,
  and relationship by owner; clients cannot assign ownership.
- Unique Google identity and compound owner/entity and owner/board indexes.
  Different accounts may each have `default-board`.
- Validate fields, enums, IDs, dates, and relationships. Tasks cannot reference
  another owner's board or subject.
- Preserve names, dates, priorities, types, descriptions, completion, colors,
  and order. Serialize instants consistently to avoid shifting deadlines.
- Confirmed board deletion cascades to its contents. Subject deletion preserves
  tasks without that subject. Preserve the final board.
- Initialize providers per account; clear state/selection on logout. Ignore
  stale account responses and older overlapping refreshes.
- Show loading/errors accurately, preserve failed forms, and make retries
  idempotent. Detect stale revisions and reload rather than overwrite silently.
- Refresh on startup, resume, and explicit request. Collaboration and live push
  are excluded; offline behavior is defined by Q04.

### Acceptance criteria

1. Create/edit/complete/delete/order survive closing and reopening.
2. A retrieves Windows data on Android and vice versa after refresh; B is separate.
3. Two-user API tests cover listing, ID access, relationships, modification,
   deletion, ordering, and rejection of forged `ownerId`.
4. Distinguish invalid sessions, unreachable API, and database failures without
   silent loss or false save-success messages.
5. Switching accounts removes all visible prior-account data.
6. Confirmed imports/retries are atomic and idempotent, preserve original data
   and relationships, and never assign a source to another account automatically.
7. Explain stale-edit conflicts to the user.

### Q04 — Offline behavior

- A. Online writes and an account-specific read cache (**recommended for this
  release**): simpler recovery and API-confirmed saves. Require connectivity if
  no authorized cache exists.
- B. Offline edits and later sync: persistent account queues, retry/deletion
  handling, and conflict resolution.

User decision, translated: read the latest copy and wait for connectivity to edit.
Block writes and explain the state. Cached data require a valid session; logout
and account switching never expose another user's cache. No offline write queue.

## B03 — API, configuration, and test environment

### Scope and acceptance criteria

Provide a locally runnable API with validated environment variables, database
connections/indexes, sanitized errors, and separate liveness/database readiness.
Do not log tokens, credential-bearing URIs, or credential-bearing request bodies.

1. Document startup with Atlas and missing-setting errors without exposing secrets.
2. Windows/Android connect to the same API/database with correct URLs.
3. Restart preserves data without relying on the API's local filesystem.
4. Flutter builds/tracked files contain no private database URI/password.
5. Document other Android certificate registration before distribution and
   distinguish debug signing from production signing.

Windows defaults to `http://127.0.0.1:3000`; a standard emulator uses
`http://10.0.2.2:3000`. Physical phones use USB reversal with a localhost build or
an accessible LAN listener. Document INTERNET permission and LAN firewall setup.
HTTP is development-only in Android debug builds; public distribution needs HTTPS.
Secrets belong only in ignored server configuration; tracked examples are blank.

## External setup instructions

### Google Cloud

1. Open <https://console.cloud.google.com/> with the project owner's account.
2. Create/select a project; record its **Project ID**, which can differ from its
   display name.
3. In **Google Auth Platform → Branding**, use `microplanner` and configure support
   and contact email.
4. Select **External** audience. Start in **Testing** and add test accounts.
5. Request only `openid`, `email`, `profile`; the latter two may appear as
   `userinfo.email` and `userinfo.profile`.
6. Provide Project ID, support email, actual publishing status, and confirmation
   of test accounts. Never provide Google passwords.
7. In **Clients → Create client**, create all three clients in the same project:

| Purpose | Type | Suggested name | Information/configuration |
|---|---|---|---|
| Windows | Desktop app | `microplanner Windows` | Desktop Client ID; app handles loopback/PKCE |
| Android API audience | Web application | `microplanner API` | Web Client ID as `serverClientId`; no browser origins/redirects needed |
| Android development | Android | `microplanner Android Debug` | Package, SHA-1, and Android Client ID |

Client IDs are public identifiers ending in `.apps.googleusercontent.com`. Keep
any downloaded JSON outside Git; provide only its path if it contains secrets.
This project's Desktop exchange requires `GOOGLE_WINDOWS_CLIENT_SECRET` in the
private server environment. Firebase, service accounts, and Google private keys
are unnecessary.

Verified package: `com.microplanner.microplanner`. Verified debug SHA-1:

```text
01:3F:46:B9:BE:7F:2B:5E:91:14:D6:42:8B:36:EE:EC:83:A8:2D:08
```

Keytool read the certificate without changing the keystore. The current release
build also uses that debug certificate. Register the delivered certificate's
SHA-1 for another signing key or Play App Signing before distribution.

### MongoDB Atlas

1. Open <https://cloud.mongodb.com/> and create/select a project.
2. Deploy a **Free** cluster, for example `microplanner-dev`; verify the free tier.
3. In **Database Access**, create technical user `microplanner_api` with a locally
   stored generated password. Grant `readWrite` only on `microplanner`, without
   administrative/all-database privileges. This differs from the Atlas account.
4. In **Network Access**, authorize the API computer's current public IP; update
   it if it changes. The phone connects to the API, not directly to Atlas.
5. Use **Connect → Drivers → Node.js** for the SRV URI. Preserve Atlas options;
   URL-encode credentials correctly without double encoding.
6. The API creates collections/indexes; do not load sample data or create the
   domain collections manually.
7. Store credentials only in ignored local `server.env`. Provide its path,
   cluster host, technical username, database, and IP-authorization status.

Public example; real values belong only in the private file:

```dotenv
# Paste the real Atlas connection string only in the ignored server.env.
MONGODB_URI=
MONGODB_DB=microplanner
GOOGLE_WINDOWS_CLIENT_SECRET=
```

## Implementation and verification — 2026-10-22

The user authorized the whole plan with the reply “Implementa”. Implementation
followed B03 → B01 → B02, preserving existing initialization work and the agreed
functional decisions.

### API, identity, and data

- Fastify, official MongoDB driver, Zod, rate limits, and sanitized errors.
- Real Atlas authenticated ping, writes, transaction commit/rollback passed;
  verification removed only its own temporary collection.
- Node initially returned `querySrv/ECONNREFUSED`. Optional process-local
  `MONGODB_DNS_SERVERS=1.1.1.1,8.8.8.8` fixed discovery without changing Windows DNS.
- Real Google token verification and Windows PKCE/state/nonce/loopback.
  Opaque session tokens are hashed in MongoDB, expire after 30 days, and are
  revocable. Late authentication responses are rejected/revoked.
- Desktop initially reported `client_secret is missing`. The user saved it in
  the ignored file; an invalid-code probe reached `invalid_grant / Malformed auth
  code`. This verified configuration, not login; real access was tested later.
- Account-specific secure sessions and encrypted caches. Immediate visible-state
  cleanup; offline logout revocation retained securely for retry.
- Collections: `users`, `sessions`, `boards`, `subjects`, `tasks`,
  `oauthChallenges`, `imports`, with owner-scoped queries/indexes.
- Atomic workspace transactions, revisions, and operation IDs prevent partial
  writes, stale overwrites, and duplicate retries. Only successful remote saves
  update the confirmed cache.
- Confirmed import names the destination email, normalizes legacy relationships,
  remaps IDs, and atomically records source ownership. Original boxes remain.
- Responsive navigation/columns and scrollable task/subject dialogs support
  mobile keyboards; failed saves preserve form values and show errors.
- The user reported unreadable import actions. Contrasting container/text/button
  colors now cover the banner and confirmation. Regression tests measure at
  least 4.5:1 contrast at 1280/360 px and verify cancellation/dismissal writes
  nothing remotely.
