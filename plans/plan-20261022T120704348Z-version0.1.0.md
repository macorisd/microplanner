# PLAN 0.1.0 — Google y datos por usuario en MongoDB

## Objetivo y estado

Un único plan para las dos funcionalidades solicitadas: inicio de sesión real con
Google y guardado en MongoDB de los tableros, asignaturas y tareas de cada usuario.
La API necesaria para conectarlas forma parte del mismo plan.

- Plataformas confirmadas: **Windows y Android**.
- Entorno confirmado: **API en el ordenador del usuario para las primeras pruebas;
  MongoDB Atlas en la nube**. No hace falta contratar ni crear hosting ahora.
- Estado: implementación autorizada expresamente por el usuario («Implementa»),
  preparada en la rama del plan y verificada automáticamente. Google/Atlas
  configurados con los datos recibidos; Atlas probado con autenticación y escritura.
  Pendientes el secreto del cliente Desktop y el login con cuentas Google reales.
  La entrega se prepara como PR borrador hasta completar esa verificación manual.
- Versión actual acordada: `0.0.1`; objetivo: **`0.1.0` minor**.
- Regla expresa del usuario, 22/10/2026: antes de `1.0.0` no habrá incrementos major
  por alcance o incompatibilidad; las funcionalidades incrementan minor y los bugs
  siguen el flujo patch. La llegada a `1.0.0` será una decisión explícita de madurez.
  Desde `1.0.0` se aplicarán los incrementos habituales.

## Situación de partida comprobada en el repositorio

- Flutter/Dart con Provider. Hay proyectos nativos Android y Windows; no hay API.
- `AuthService` simula un usuario; `enableAuthentication=false` omite el acceso.
- `BoardsProvider` y `TasksProvider` abren cajas Hive globales: `boards`, `subjects`
  y `tasks`. Se cargan antes de conocer la identidad del usuario.
- Los modelos ya tienen identificadores y relaciones por tablero/asignatura,
  pero no propietario. Existe el ID compartido `default-board` y datos antiguos
  sin `boardId` o con el campo legado `subject`.
- Android usa actualmente `com.microplanner.microplanner`. Tanto debug como release
  usan la firma debug; no se ha preparado una firma de distribución.
- Hay cambios previos de inicialización en `pubspec.yaml`,
  `windows/runner/Runner.rc` y `.github/`. El usuario también ha añadido a
  `.gitignore` la regla `*.env`. Este trabajo solo añade/actualiza el plan y
  contexto local; no incorpora ni modifica esos cambios.

## Propuesta técnica para aprobar con el plan

`Flutter (Windows / Android) → API autenticada → MongoDB Atlas`.

Google acredita la identidad. La API valida esa identidad, crea o recupera la
cuenta y entrega una sesión de MicroPlanner. La API es el único cliente de MongoDB;
la URI y contraseña de MongoDB nunca se distribuyen en Flutter.

- API propuesta en `server/`, Node.js con TypeScript, HTTP/JSON y driver oficial
  de MongoDB. Las librerías y versiones compatibles se fijarán al implementar.
- Autenticación Google directa, sin añadir Firebase como servicio intermedio.
- Android: integración oficial `google_sign_in`, registro Android y cliente OAuth
  web utilizado como `serverClientId` / audiencia del ID token.
- Windows: navegador del sistema, Authorization Code con PKCE S256, `state`,
  `nonce` y retorno a loopback `127.0.0.1` en puerto efímero; cliente OAuth Desktop.
  El plugin oficial `google_sign_in` no declara soporte Windows.
- Solo permisos de identidad `openid`, `email`, `profile`.
- Sesiones propias de API con expiración y revocación. Credenciales de sesión
  guardadas usando almacenamiento seguro del sistema; no en Hive sin cifrar.
- MongoDB será la fuente de verdad remota. Según Q03/Q04, ofrecer importación
  confirmada de Hive y mantener caché de lectura por cuenta; editar requiere API
  disponible. No habrá cola de ediciones offline en esta versión.

## B01 — Iniciar y cerrar sesión con Google

### Objetivo y comportamiento esperado

Sustituir la autenticación simulada por el acceso real en Windows y Android. Al
iniciar sesión se muestra el espacio del usuario autenticado; al cerrar sesión
se vuelve al acceso y se elimina del estado visible la información de esa cuenta.

### Alcance y límites

- Estados de inicio, restauración de sesión, cancelación, error, cuenta activa y
  cierre de sesión; impedir dobles intentos mientras haya un acceso en curso.
- Validación en la API mediante biblioteca oficial: firma, emisor, audiencia
  permitida por plataforma y caducidad del ID token; comprobar el `nonce` donde
  corresponda. No aceptar como identidad un email o ID enviados sin verificar.
- Identidad estable basada en el `sub` verificado de Google; registro automático
  de cuenta interna y perfil mínimo: nombre, email y foto opcional.
- Restaurar sesiones válidas y volver al acceso ante expiración/revocación.
  Cerrar una sesión debe revocarla en servidor además de limpiar el cliente.
- Activar el acceso obligatorio en el flujo de nube y retirar el texto de mock.
- El flujo de Windows cancela/cierra el listener loopback y valida el retorno.
- No incluye contraseñas propias, otros proveedores, roles, invitaciones,
  compartición de tableros ni borrado completo de cuentas.

### Criterios de aceptación

1. Una cuenta Google real accede en Windows y Android; un fallo o cancelación
   deja la aplicación en un estado recuperable.
2. La misma cuenta obtiene el mismo usuario interno en ambas plataformas.
3. Tokens manipulados, caducados o de otra audiencia reciben rechazo.
4. Reiniciar restaura una sesión válida; una sesión inválida no abre el dashboard.
5. Cerrar sesión y acceder con otra cuenta no muestra datos del usuario anterior,
   tampoco mientras llegan peticiones iniciadas antes del cambio de cuenta.

### Dependencias y preparación externa

B03 proporciona API y configuración. Se necesitan proyecto de Google Cloud,
consentimiento OAuth y los tres clientes explicados en la guía de este documento.

## B02 — Datos de cada usuario en MongoDB

### Objetivo y comportamiento esperado

Guardar y recuperar en MongoDB los tableros, su orden, asignaturas y tareas del
usuario autenticado. Al entrar en otro dispositivo con la misma cuenta deben
recuperarse los datos confirmados por la API. Otra cuenta debe tener su espacio.

### Alcance y límites

- Colecciones propuestas: `users`, `boards`, `subjects`, `tasks`, `sessions` y,
  si se aprueba importar, recibos de migración. No se crea un usuario MongoDB
  por persona: el usuario técnico de API accede a una base y la API aísla cuentas.
- Cada entidad de dominio lleva `ownerId` asignado exclusivamente por servidor.
  Todas las lecturas, cambios, borrados y relaciones filtran por el propietario.
- Índice único para identidad Google; índices por propietario e identificador,
  y por propietario/tablero para consultas. Admitir `default-board` de cuentas
  distintas mediante claves compuestas o su conversión explícita.
- Validar campos, enumeraciones, fechas y relaciones en la API. Una tarea no
  puede apuntar al tablero/asignatura de otro usuario.
- Preservar nombres, fechas, prioridades, tipos, descripción, finalización,
  colores y orden. Documentar la conversión de fechas para no desplazar plazos.
- Propuesta de integridad al borrar: eliminar el contenido de un tablero tras
  confirmación; al borrar una asignatura conservar tareas sin esa asignatura.
  Actualizar los textos de confirmación para reflejar el efecto real.
- Adaptar proveedores a repositorios/API y a inicialización por sesión; limpiar
  listas y selección al salir. Cancelar o ignorar respuestas de sesiones antiguas.
- Mostrar cargas y errores de conexión/guardado; no confirmar en la interfaz un
  guardado remoto que ha fallado. Reintentos no deben duplicar operaciones.
- Concurrencia mínima: detectar revisiones obsoletas y recargar antes de aceptar
  otra edición; no sobrescribir cambios de otro dispositivo silenciosamente.
- Recarga al abrir, volver a primer plano o refrescar. No incluye colaboración,
  actualizaciones instantáneas entre dispositivos ni colas offline salvo Q04.

### Criterios de aceptación

1. Crear/editar/completar/borrar y ordenar persiste tras cerrar y volver a abrir.
2. La cuenta A recupera en Android los datos guardados desde Windows, y viceversa,
   tras una recarga; la cuenta B tiene sus propios datos.
3. Pruebas de API con dos usuarios confirman aislamiento al listar, acceder por ID,
   crear relaciones, modificar, borrar y reordenar; se rechaza falsificar `ownerId`.
4. Se distinguen sesión inválida, servidor inaccesible y fallo de MongoDB sin
   pérdida silenciosa ni mensajes de éxito falsos.
5. Un cambio de cuenta elimina cualquier exposición de datos de la anterior.
6. Si se aprueba migrar, importar dos veces o reintentar tras un corte no duplica
   datos ni deja entidades sin relaciones. Los originales se conservan hasta
   verificar la importación completa y no se asignan a una cuenta sin confirmación.
7. Una edición basada en una revisión antigua se detecta y explica al usuario.

### Dependencias

Identidad/sesiones de B01 y conexión de B03. Q03/Q04 están resueltas: importación
con confirmación y caché de lectura sin cola de escritura offline.

## B03 — API, configuración y entorno de pruebas

### Objetivo y comportamiento esperado

Disponer de una API ejecutable en este ordenador que conecte clientes Flutter con
MongoDB Atlas. Una guía reproducible documentará arranque, variables y acceso desde
Windows, emulador Android y un móvil real en la misma red.

### Alcance y límites

- Estructura de API, configuración validada al arrancar, conexión de MongoDB,
  índices, manejo coherente de errores y comprobaciones de disponibilidad.
- Separar liveness y disponibilidad real de MongoDB; no dar servicio de datos
  como preparado si falla la base. No registrar tokens ni URI con credenciales.
- Variables públicas Flutter: URL de API e IDs OAuth que correspondan.
- Variables privadas servidor: `MONGODB_URI`, `MONGODB_DB`, configuración de
  sesiones y cualquier secreto OAuth requerido en el canje de código.
- Windows local: `http://127.0.0.1:3000` como propuesta. Emulador Android estándar:
  `http://10.0.2.2:3000`. Móvil físico: IP LAN del ordenador, misma red y API
  escuchando en interfaz accesible. Verificar firewall y permiso INTERNET Android.
- El HTTP local solo se habilita para desarrollo. Una futura publicación debe usar
  HTTPS y configuración propia; no habilitar tráfico HTTP general en release.
- Guardar secretos exclusivamente en un fichero local ignorado o entorno del
  servidor. Versionar únicamente ejemplos sin valores reales.
- No incluye despliegue en Render u otro proveedor, compra de dominio, distribución
  en Google Play/Microsoft Store ni cambios de planes de pago.

### Criterios de aceptación

1. La documentación permite arrancar la API local con Atlas y detectar variables
   ausentes sin exponer secretos.
2. Windows y Android conectan con la misma API y base usando sus URL correctas.
3. Reiniciar API no pierde datos ni requiere usar su disco como almacenamiento.
4. El build Flutter y los ficheros versionados no contienen contraseña ni URI privada.
5. Existe procedimiento documentado para registrar otras firmas Android cuando
   se prepare una distribución; no confundir la firma debug actual con producción.

## Guía exacta de preparación para el usuario

### 1. Google Cloud: proyecto y consentimiento

1. Entrar en <https://console.cloud.google.com/> con la cuenta propietaria.
2. Crear o elegir un proyecto, por ejemplo `microplanner`. Anotar su **Project ID**,
   que puede tener un sufijo y no coincide necesariamente con el nombre visible.
3. Ir a **Google Auth Platform → Branding / Get started**. Nombre: `MicroPlanner`;
   email de soporte y de contacto: el correo elegido por el propietario.
4. Audience: **External**, para permitir cuentas ajenas a una organización.
   Empezar en **Testing** y añadir las cuentas que se usarán en las pruebas.
5. Data Access: solicitar solo `openid`, `email` y `profile` (los dos últimos pueden
   aparecer como `userinfo.email` y `userinfo.profile`).
6. Enviar Project ID, email de soporte, estado de publicación del consentimiento
   y confirmación de las cuentas de prueba. Nunca la contraseña de Google.

### 2. Google Cloud: tres clientes OAuth en el mismo proyecto

En **Google Auth Platform → Clients → Create client**:

| Cliente | Tipo | Nombre sugerido | Configuración | Qué comunicar |
|---|---|---|---|---|
| Windows | Desktop app / Aplicación de escritorio | `MicroPlanner Windows` | La app gestionará retorno loopback y PKCE | Client ID Desktop |
| Audiencia API usada por Android | Web application / Aplicación web | `MicroPlanner API` | En esta integración solo se usa su Client ID como `serverClientId`; dejar vacíos origins/redirects | Client ID Web |
| Android debug | Android | `MicroPlanner Android Debug` | Paquete y SHA-1 indicados debajo | Client ID Android; confirmar paquete y SHA-1 |

Todos los Client ID suelen terminar en `.apps.googleusercontent.com` y se pueden
compartir como configuración pública. Descargar los JSON si se desea y guardarlos
fuera de Git; si alguno contiene `client_secret`, comunicar solo su ruta local,
no pegar su contenido. No hacen falta Firebase, cuenta de servicio ni clave privada
de Google para esta propuesta.

**Paquete Android comprobado:** `com.microplanner.microplanner`.

**SHA-1 debug comprobada en este ordenador:**

### 3. MongoDB Atlas: cluster, usuario técnico y acceso de red

1. Entrar o registrarse en <https://cloud.mongodb.com/>.
2. Crear o elegir proyecto `microplanner` y desplegar un cluster **Free** (antes
   llamado M0), por ejemplo `microplanner-dev`, en una región europea disponible.
   Confirmar que la opción elegida indica gratuita, sin contratar un tier superior.
3. En **Database Access / Database Users**, crear el usuario técnico
   `microplanner_api`, autenticación por contraseña. Generar una contraseña y
   guardarla localmente.
4. Darle el rol `readWrite` limitado a la base **`microplanner`**, mediante
   privilegios específicos; no permisos de administrador ni de todas las bases.
   Este usuario es para la API, distinto de la cuenta que accede al panel Atlas.
5. En **Network Access / IP Access List**, añadir **la IP pública actual del
   ordenador que ejecutará la API**, usando Add Current IP Address. Si cambia,
   actualizar la entrada. No hace falta autorizar la IP del móvil: conecta a la API.
6. En el cluster: **Connect → Drivers → Node.js**; copiar la URI SRV que ofrece
   Atlas. Usar la base `microplanner` y conservar las opciones generadas por Atlas.
7. No es necesario crear manualmente tableros/colecciones ni cargar sample data:
   la API creará colecciones e índices. El nombre de base se puede usar en los
   permisos antes de que exista físicamente.
8. Guardar la URI completa con su contraseña en un fichero privado fuera del repo,
   por ejemplo `C:\Users\macor\.microplanner\server.env`. Comunicar **la ruta**,
   el host del cluster, el usuario técnico, la base y que la IP está autorizada.
   En el chat, cualquier URI se comparte solo con contraseña sustituida por
   `<OCULTA>`. Codificar los caracteres especiales de usuario/contraseña al formar
   una URI; el driver debe recibir las credenciales correctas, sin dobles escapes.

Contenido esperado del fichero privado, con los valores reales solo en disco:

```dotenv
MONGODB_URI=mongodb+srv://microplanner_api:<PASSWORD_URL_ENCODED>@<HOST>/<DATABASE>?<OPCIONES_DE_ATLAS>
MONGODB_DB=microplanner
```

La ruta anterior era una recomendación fuera del repositorio. El usuario eligió
finalmente `C:\Users\macor\Desktop\GitHub\microplanner\server.env`; se ha
comprobado que existe, está ignorado por la regla `*.env` de `.gitignore` y no está
versionado. Se conservará esa ubicación sin copiar sus secretos al plan. Durante
la implementación se documentará cómo cargarlo en el servidor.
