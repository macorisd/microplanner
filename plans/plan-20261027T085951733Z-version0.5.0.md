# microplanner 0.5.0 - Android board carousel and direct task editing

## Outcome and constraints

Give Android a flat, layered board carousel using the application's three existing
semantic colors, opening Upcoming by default. Add an invisible left-edge sidebar
activation region and edit Android tasks by tapping their cards instead of an
edit button. Remove the redundant spinner next to Refresh while retaining the
floating cloud notification.

Baseline: v0.4.0, PR 5 merged at 1000d5779fb5372b2c401296a784c358cd83aed9.
Target: minor 0.5.0, next Android build number 12.
Proposed implementation branch: feature/android-board-carousel.

Keep all existing palette values, task/subject colors, compact card spacing,
48 dp task controls, Google account/photo, cloud ownership, offline read-only
behavior, system bars and user data. Windows keeps its column layout and
hover-revealed task editing controls. The redundant toolbar spinner removal
applies to both platforms; the floating notification remains the status feedback.

The user explicitly requests design questions for meaningful user-facing choices.
Do not turn recommendations into decisions. Record each answer in its block,
resolve dependent questions, then request approval before implementing revised
design decisions. The initial plan was approved and local implementation began;
the user's rotation clarification revises B01 below.

## Baseline findings (v0.4.0)

- Android used a PageView with viewportFraction 0.92, ordered Complete,
  Late, Upcoming and initially showing Complete. This does not deliver the
  requested initial page or rotational motion.
- The compact Scaffold already has Flutter's default edge-drag drawer handling.
  Flutter 3.38.6 defaults that area to 20 logical pixels plus the left safe inset.
  The carousel and a deliberate edge region need explicit gesture coordination.
- TaskCard already separates completion and delete callbacks from its main
  InkWell, but the card tap is not currently wired to the edit form.
- DashboardScreen displays an additional loading/saving spinner before Refresh
  even though AccountDashboard already overlays the cloud-status notification.

## B01 - Android three-sheet carousel

Arrange Completed | Late | Upcoming spatially from left to right and open
Upcoming initially. Swiping the finger right reveals Late, then Completed;
swiping left returns toward Upcoming. Use the existing green, yellow and blue
semantic colors respectively. Use the Android label Completed while retaining
Windows's existing Complete label.

Keep columns flat and parallel to the screen throughout the transition, with no
tilt, skew or angular perspective. Convey depth through overlapping layers and
subtle uniform scaling: initially Late sits behind Upcoming and Completed behind
Late. Moving through the carousel brings the destination layer forward and moves
the departing layer out to the right. Never recycle passed columns behind the
active one: Late shows only Completed behind it, and Completed shows no further
layer. Keep the active card nearly full-width and
readable, with left-edge glimpses of the layers behind it. Stop at Completed and
Upcoming rather than allowing navigation to wrap in a loop.
Add a three-option direct selector to the left of New Task on Android, with its
active state synchronized to rotation. Selecting a destination animates the same
carousel to that destination, including intermediate turns when appropriate.
Use three icons (completion, warning, clock) in the existing category colors,
with accessible names and active state. Retain New Task text when space permits,
using its compact plus button on narrow/large-text layouts when needed.
Do not add separate position dots.
Align the selector's left edge exactly with the active column's left edge when
the carousel is settled, including after resizing or rotating the device.
Keep the active header's label and count readable. Return to
Upcoming when the selected board changes, including when returning to a previous
board; ordinary refreshes and task updates preserve the active category.

Acceptance criteria:

- The initial Android board view is Upcoming, including after a fresh app start.
- All three states remain reachable, including empty columns, with the active
  state identified by its header and the left neighbor partially visible where
  present. Preserve accessible navigation semantics and the direct selector.
  Avoid a full three-column desktop layout.
- Preserve vertical task scrolling, compact readable cards, task ordering,
  completion transitions, scroll state during ordinary cloud refreshes and
  existing empty-header colors.
- Keep input responsive during repeated swipes and board changes. Layer movement
  follows the gesture and settles promptly, with appropriate depth ordering and
  inactive card hit testing. Reduce spatial motion for reduced motion preferences.
  Columns remain flat even mid-gesture. No idle animations.
- Drag release snaps precisely to one full column with bounded endpoints and no
  intermediate resting position. Keep the selected destination and visible column
  synchronized during repeated gestures or rapidly changed manual selections.
- The selector and New Task remain reachable together at narrow widths and large
  text sizes, with appropriate touch targets and no overlap with tasks/system bars.
- No palette replacement, heavy blur or unnecessary whole-list opacity layers.
- Windows's column order and layout are unchanged.

### Q01 - Finger direction versus spatial column order

When Upcoming is visible, which gesture should reveal Late and then Completed?

- A. Swipe the finger left: Upcoming -> Late -> Completed (**recommended**,
  directly follows the user's description of the gesture).
- B. Arrange Completed | Late | Upcoming from left to right, like the logo's
  colors; from Upcoming, swipe the finger right to reveal Late then Completed.

User answer (translated): arrange Completed | Late | Upcoming from left to right,
like the logo's colors; from Upcoming, swipe the finger right.
Consequence: use that spatial order with Upcoming initially at the right end.

### Q02 - Visual treatment

Which presentation should define the carousel?

- A. Partially overlapping sheets with a dominant active sheet, visible colored
  neighbors and subtle depth (**recommended**, connects the interface to the logo).
- B. Flat, nearly full-width pages with a glimpse of neighboring pages and a
  compact position indicator; simpler visual treatment.

User answer (translated): flat, nearly full-width pages, showing a little of the
left neighbor and no position indicator.
Initial consequence: accepted modified option B and omitted the indicator.
Subsequent user clarification (translated): the current behavior feels like
horizontal scrolling; the user wants something rotating. The earlier inference
that flat presentation ruled out rotational motion is withdrawn. Q05 replaces
the motion decision. The user subsequently requested the direct selector in Q07,
superseding the no-selector interpretation. A small left peek and readable settled
cards remain required; omit additional position dots. Retain accessible headers,
counts and navigation semantics.

### Q03 - Changing boards during a session

What should happen to the active carousel state when switching boards?

- A. Open Upcoming on each board change (**recommended**, consistently prioritizes
  pending work and makes the entry state predictable).
- B. Open Upcoming on app start, then keep the currently selected state when
  changing boards during the same session.

User answer (translated): return to Upcoming on board changes, as recommended.
Consequence: reset the page controller for a changed board/account; ordinary
refreshes and task updates must not reset the user's active page.

### Q05 - Rotation model

Which physical motion best matches the intended carousel?

- A. A wheel around a vertical axis: the active column rotates away in perspective
  and the next rotates forward to face the user (**recommended**, gives a carousel
  turn while keeping settled task cards straight and readable).
- B. A fan of cards: columns rotate in the screen plane around a point near the
  bottom, like turning a hand of cards; the active column settles upright.

User answer (translated): a 3D wheel, with each column rotating around a vertical
axis; one tilts away and the next rotates to face the user.
Consequence: implement perspective and horizontal placement around the vertical
rotation axis, with stable readable resting cards and the direct selector in Q07.
This initial interpretation is superseded by Q08 after the user tried the build.

### Q06 - Endpoints or a continuous loop

What happens after reaching Completed and continuing in the same direction?

- A. Stop at Completed; reverse the gesture to return through Late to Upcoming
  (**recommended**, preserves the agreed spatial order without an unexpected wrap).
- B. Continue around to Upcoming, repeating the three states as a rotating loop.

User answer (translated): stop at Completed; reverse the gesture to return.
Consequence: clamp rotation to the three agreed states; no wraparound state.

### Q07 - Direct selector presentation

How should the selector to the left of New Task present the three destinations?

- A. Three icons: completion, warning and clock, with current colors and accessible
  names (**recommended**, compact and keeps the New Task label when space permits).
- B. Three text options: Completed, Late and Upcoming; reduce New Task to its plus

Keep both navigation modes synchronized; gestures must snap precisely to a column.

### Q09 - Selector alignment

User instruction (translated): the manual selector's left edge must align with
the column's left edge when it is fixed in place.
Consequence: derive both positions from the same responsive leading inset.

### Q10 - Honest finite-depth hints

User instruction (translated): when navigating to a column on the left, do not
show the displaced column behind it, because that incorrectly suggests further
navigation to the left of Completed.
Consequence: remove layer recycling. Passed columns leave to the right and remain
available through reverse gestures or direct selection, retaining their list state.

## B02 - Invisible left-edge sidebar region on Android

Reserve a narrow, invisible, full-height app-content region at the left edge for
opening the sidebar without pressing the existing burger button. Coordinate it
with the chosen carousel direction and retain the burger as an accessible fallback.
Open by dragging inward from the strip only; a tap on it must not open the drawer.
Validate 36 dp of app gesture space just inside Android's Back
region. Allow a small fallback for skins reporting a zero Back inset; do not
consume extra visible layout width or override the operating system gesture.

Acceptance criteria:

- The region opens the existing sidebar reliably in portrait and landscape.
- Gestures starting outside the region navigate the carousel normally; vertical
  task scrolling and checkbox/delete taps remain usable.
- Do not intercept dialogs, the open drawer or Android's system bars. Preserve
  the operating system's Back gesture; verify actual coexistence on the Redmi
  rather than promising an app can receive gestures consumed by Android.
- No visible handle or changed colors. Accessible navigation remains available.
- No change to Windows navigation.

### Q04 - Activating the invisible region

How should the invisible strip open the sidebar?

- A. Tap it or drag inward from it (**recommended**, supports either shortcut
  while keeping ordinary carousel gestures outside the strip).
- B. Drag inward only, like a conventional drawer edge gesture.
- C. Tap only, avoiding an additional app-level horizontal drag interaction.

User answer (translated): only by dragging from the strip inward.
Consequence: recognize an inward horizontal drag, not a tap. Retain system
navigation and avoid accidental openings during vertical scroll or card taps.

<!-- md-question {"id":"Q11","block":"B02","status":"answered","decision":"Widen the invisible drawer strip inward to provide more room beyond Android Back; use 36 dp of app drag space plus the system inset/fallback."} -->
### Q11 - Wider inward gesture region

User instruction (translated): make the invisible left-side strip somewhat wider,
because the current region almost overlaps Android's Back gesture.
Consequence: increase app drag space from 20 to 36 dp, beyond the reported system
inset (or 20 dp fallback on the Redmi). Do not override Back or add visible width.

## B03 - Direct Android task editing

Remove edit buttons from Android task cards and open the existing edit dialog on
a normal card tap. Keep completion and deletion as separate controls. This is an
explicit user decision and does not require asking about long press or double tap.

Acceptance criteria:

- Tapping card content opens editing; tapping its checkbox only toggles completion;
  tapping Delete only opens its existing confirmation.
- No edit icon or empty reserved edit-button slot remains on Android.
- Keep Delete visible and retain existing compact layout and touch targets.
- Starting a scroll or carousel swipe on a card must not open editing on release.
- Edit opens without selecting the name or automatically opening the keyboard.
- Offline/read-only state prevents editing, completion and deletion as before.
- Windows keeps its existing hover edit/delete controls and card-tap behavior.

## B04 - One cloud loading notification

Remove the animated spinner immediately before the Refresh button on both compact
and wide dashboard toolbars. Preserve the existing floating notification, refresh
action, loading/saving protections and error/offline feedback.

Acceptance criteria:

- Loading/saving no longer adds the redundant toolbar spinner or shifts Refresh.
- The floating cloud-status notification remains the loading feedback, without
  displacing content. Do not remove its own activity indicator.
- Retain startup and retry feedback when no account data is available yet.
- Refresh remains disabled while its request is in flight; no duplicate writes
  or requests introduced by the presentation change.

## Implementation and validation

The user approved the initial plan, clarified the rotational motion and added a
direct selector, then explicitly approved the updated complete scope. Work is on
feature/android-board-carousel from main v0.4.0. Q02/Q05 remain as withdrawn history;
Q06 through Q11 record the final endpoints, selector, flat-depth treatment,
alignment, honest layer hints and wider drawer gesture region.

- B01: a bounded animation controller drives translation and uniform scale for
  three stable, parallel column surfaces. Paint nearer surfaces last; keep passed
  columns offstage on the right without recycling them behind the stack.
  Inactive/moving columns cannot receive task
  taps or focus. Gesture release settles exactly on an integer destination;
  short drags return, longer drags/intentional flings reach one adjacent column.
  Manual selection uses the same controller and accepts destination changes during
  animation. Reduced motion removes spatial scaling and makes manual selection immediate.
- B01: Upcoming is initially active; a board/account identity key resets it on
  selection changes. All three list states are retained while navigating.
  Three 48 dp selector icons sit left of New Task; its label becomes a plus button
  when necessary at narrow widths or large text sizes. The selector and active
  column share the same leading inset. Palette values are unchanged.
- B02: Android's drawer recognizes an inward edge drag. The target includes 36 dp
  inside the reported Back region, with a 20 dp fallback because the Redmi reports
  zero. No system gesture exclusion or settings change is used. The widened inward
  drag at native x=132 opened the drawer, beyond the former target; a tap did not
  open it in interaction tests. The extreme-edge gesture
  still invokes Android Back, as observed at native x=45.
- B03: Android card taps open editing; the edit icon and its reserved slot are
  removed. Completion and Delete stay separate. Windows retains hover actions.
- B04: both dashboard toolbar spinners are removed. The floating cloud notice,
  startup/retry feedback and request-in-flight protections remain.
