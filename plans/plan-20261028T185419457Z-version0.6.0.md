## B01 — Restore the last active board

On reopening the app, restore the board most recently selected by that account.
Remember this locally per account and device: Windows and Android have separate
starting boards, and board navigation does not trigger cloud workspace writes.
Separate each Google account's preference. Remember newly created/automatically
selected boards as well as deliberate sidebar selections. Store a stable board
ID; renaming or reordering a board must not break restoration.

If the remembered board no longer exists, use the first available board in the
existing order and update the preference when the relevant data are confirmed.
Do not overwrite a valid preference with a temporary startup fallback, allow an
old asynchronous read to override a newer selection, or apply one account's
preference to another. Offline startup should use the last available account
copy. Preference storage failures must not prevent board navigation or change
task data.

Restore the board's task view; Android still starts its carousel on Upcoming.
Restoring the Subjects management screen or the carousel page is outside scope.

Acceptance: relaunch, sign-out/sign-in, account switching, rename/reorder,
deleted/missing boards, slow preference reads, offline startup and storage
failure behave consistently. Cross-device behavior follows Q01.

<!-- md-question {"id":"Q01","block":"B01","status":"answered","decision":"Remember the last board locally per Google account and device."} -->
### Q01 — Where is the last-board preference remembered?

- A. Per account and device (**recommended**): Windows and Android each reopen
  where that account left off on that device; using one does not change the
  other's starting board.
- B. Shared by the account in the cloud: both devices reopen the board most
  recently selected on either device, with a local offline fallback.

User answer: A, per account and device. Windows and Android each remember their
own last board. Consequences: use account-scoped local preference storage, with
no new cloud preference endpoint or cross-device navigation synchronization.

## B02 — Clear completed tasks

Add a discreet trash icon immediately to the left of the completed-task counter
in that column's header on both platforms. Its tooltip and accessible name are
exactly `Clear Complete Tasks`. Use the current colors, an accessible target and
an unobtrusive visible icon. Do not add the action to Late or Upcoming.

Disable it when there are no matching completed tasks, editing is unavailable,
or its operation is pending. Follow Q02 for its deletion scope and Q03 for the
confirmation/recovery flow. Preserve all incomplete tasks, boards, subjects and
out-of-scope tasks. Explain the affected count/scope before destructive work.
The selected scope is the active board only. Open a confirmation showing its
name and the number of completed tasks; cancelling performs no mutation. There
is no immediate-delete/Undo flow in this version.

Use one account-bound, revision-checked workspace mutation rather than one
request per task. Freeze the intended IDs for the chosen action and reconcile
against the latest snapshot; never silently expand a confirmed deletion to new
tasks completed afterwards. Do not delete an intended task that has since been
marked incomplete. On a conflict/error, retain current confirmed data and show
an actionable result. Block duplicate submission and premature dismissal while
the actual write is pending, consistent with 0.5.2.

Acceptance: correct placement, tooltip, zero/offline/pending states, accurate
scope/count, cancellation/recovery, one write, preservation of other data,
concurrent changes, account switches and compact/large-text layouts.

### Q02 — Which completed tasks does the button clear?

- A. Only the active board (**recommended**): matches the column and counter
  beside the button, preserving completed tasks in other boards.
- B. All boards in the current account: a global cleanup, explicitly identified
  in the action flow to avoid confusion with the current board's counter.

User answer: A, only completed tasks in the open board. Consequences: bind the
confirmation and deletion to that board's stable ID and leave every other
board's tasks untouched, even if the current selection later changes.

<!-- md-question {"id":"Q03","block":"B02","status":"answered","decision":"Require confirmation displaying the affected task count and board."} -->
### Q03 — How is bulk deletion confirmed or recovered?

- A. Confirmation with the count and board/scope (**recommended**): consistent
  with existing deletion dialogs; nothing is deleted if cancelled.
- B. Immediate action with an Undo period: more direct, but requires defining
  the undo window and what happens if the app closes or connectivity changes.

User answer: A, ask for confirmation with the count and board. Consequences:
reuse the existing guarded destructive confirmation pattern. No Undo duration,
deferred deletion or recovery-window decisions are needed.

User wording refinement during implementation: remove the additional sentence
about preserving incomplete tasks/other boards. The confirmation now contains
only `Delete N completed task(s) from "Board"?`; deletion scope is unchanged.

## B04 — Prevent unwanted text focus restoration

Investigate and correct focus handling when moving from an editable field to
date/time pickers, subject/type dropdowns, priority/color selectors and other
non-text controls. A date/time picker must not restore the previous title or
description focus and reopen the Android keyboard on confirm or cancel. Apply
the same rule across affected forms and both platforms.

Keep explicit text entry functional, including manual date/time entry and
Windows keyboard navigation. Preserve entered values, the pending-write locks,
validation limits and the intended initial focus behavior (for example, Android
Edit Task does not initially open the keyboard).

Acceptance: focus title and description, open/close each affected selector by
confirm/cancel/back, and verify that the parent text field remains unfocused and
the keyboard stays hidden until explicitly requested. Check subject name/color
interaction, repeated picker opening and normal typing/Tab navigation.

## Investigation notes

- BoardsProvider currently keeps only in-memory `_currentBoardId`, resetting on
  account changes; no board-selection preference exists yet.
- The shared column header already renders the counter; clearing can be added
  without changing the Android carousel or the current column colors.
- Priority is currently a bare text indicator beside the title, whereas delete
  uses platform-dependent action targets; those centers differ.
- `PendingActionState.pickOnce` prevents duplicate pickers but does not release
  parent text focus. Dropdowns and subject color taps likewise lack an explicit
  focus handoff. Confirm the exact restoration paths with regression tests.

## Implementation and validation

The user answered Q01/Q02/Q03 and explicitly approved implementing the complete

### Implemented behavior

- B01: device-local secure storage uses account-specific keys and stable board
  IDs. Account-specific write queues preserve rapid selections and sign-out
  boundaries. Startup waits for preference resolution, rejects stale reads,
  restores cached/offline boards, and only persists missing-board fallbacks
  after cloud confirmation. Failed/stalled preference reads cannot indefinitely
  block navigation or overwrite unread preferences. Selection does not write to
  the cloud workspace.
- B02: only the completed header has the discreet, accessible trash action. It
  shows a guarded count/name confirmation and executes one revision-checked
  mutation for the captured board/IDs. Newly completed and subsequently
  incomplete tasks are preserved. Empty/offline/pending actions are disabled;
  conflicts and stale confirmations retain current confirmed data. Large batch
  removal resets the rendered list instead of creating hundreds of outgoing
  row animations; normal small task updates keep their existing animations.
- B03: platform-specific trailing slots align the priority center with the
  delete icon, with an 8-pixel title gap. A single fitted priority line prevents
  wrapping or extra vertical spacing with large text; existing compact card
  regression checks remain intact.
- B04: selectors release the primary focus before opening a child route or
  changing a non-text value. Merely unfocusing the surrounding scope retained
  the previous input in its focus history; releasing the actual focused node
  fixes restoration after return. Applies to title/description, date/time,
  subject/type dropdowns and priority/color controls. Explicit text entry and
  Windows Tab/Space/arrow-key navigation remain available.
