# Background actions and task transitions - 0.9.0

## Outcome and constraints

On Windows and Android, submitting a valid action closes its form or confirmed
prompt immediately and leaves navigation and unrelated actions available while
one floating synchronization notice reports progress. This applies throughout
workspace actions, including create/edit/delete task, boards, subjects, bulk
clear, import and reorder where applicable. Keep existing account isolation,
validation, destructive confirmations, local-only navigation preferences, colors,
synchronization notice design and data. Do not move the user's scroll position,
change their board/column selection, or navigate to a newly created board after
another explicit navigation while the action was pending.

A single network snapshot/revision is currently shared by all workspace data.
Design explicit per-action intents and reconcile them with the authoritative
server state; never apply stale full snapshots over later edits. Use account and
entity identities and stable operation IDs, serialize conflicting writes, and
preserve server revision and idempotency protections. A timeout is an unknown
outcome, not proof that the server failed: reconcile or safely retry using the
same operation identity before calling it failed or replaying a destructive act.
The existing client generates an operation ID inside each save attempt, and the
server remembers only the latest 50 IDs per account. A durable queue must not
assume an old missing ID proves non-commit: design and test an appropriate
receipt/reconciliation strategy, including expiry and more than 50 intervening
remote operations. Preserve atomicity and avoid storing session tokens in the
queue. A device or OS crash can interrupt a local write; acceptance and recovery
must not silently report such an action as confirmed.

## B03 - Safe operation queue and lifecycle

Accept valid actions without blocking other independent work. Disable the controls of a task with an unfinished action, including during its base transition; never accept or silently duplicate a second action on that same task through a stale surface. Distinguish queued,
sending, confirming, successful, confirmed failed and unknown outcomes. The
visible sync notice covers all outstanding accepted work without flickering
between operations. Maintain causality and ordering for dependent actions, isolate
accounts, verify target identity/preconditions and do not resurrect deleted data
or lose later edits on conflicts. Define account switch, shutdown, restart,
network loss, duplicate requests and server conflict behavior before coding.
Offline access remains read-only for new actions unless explicitly changed.

### Q01 - Leaving or closing while actions are pending

- A. Persist accepted actions securely on this device and resume/reconcile them
  after reopening or signing back into the same account (recommended: protects
  submitted work even if the app is closed or Android removes its process).
- B. Keep them only while the app runs and warn before sign-out/normal close;
  an OS process kill can still interrupt them.

User answer: A. Persist securely and resume only for the same account.

<!-- md-question {"id":"Q02","block":"B03","status":"answered","decision":"Disable controls for the affected task until its current operation finishes; independent actions remain available."} -->
### Q02 - Multiple actions on the same pending task

- A. Accept and queue further actions on that task in order, resolving dependencies
  and reporting any action that cannot safely follow a failed predecessor
  (recommended: consistent with free interaction).
- B. Temporarily disable actions on the affected task; allow work everywhere else.

User answer: B. Disable the affected task until its previous action finishes; other tasks and navigation remain available.

## B01 - Immediate dialog dismissal and recovery

Validate and capture each operation before closing its dialog. Closing is not a
claim of success: confirmed failure needs an actionable notice outside the form,
without losing submitted text or incorrectly erasing later successful work.
Keep duplicate-submit guards across the dismissal and preserve confirmation of
irreversible actions. Cover all relevant forms and inline actions, not only task
creation. Report multiple independent errors without silently overwriting them.

<!-- md-question {"id":"Q03","block":"B01","status":"answered","decision":"Show errors with the option to reopen the retained draft or retry when safe."} -->
### Q03 - Recovering an unsuccessful form submission

- A. Show the failed action in the notice with options to reopen its preserved
  draft or retry when safe (recommended: avoids losing the user's text).
- B. Show the failure and require the user to enter the data again.

User answer: A. Show errors and allow reopening the preserved draft or safe retry.

## B02 - Coordinated task transitions

Maintain task-level transition state independent of lazily built cards, viewport,
board selection and Android carousel page. The source card fades from white to
its destination color and shows a subtle moving nebula while work is outstanding;
its base animation always finishes. Until synchronization confirms the change,
it remains in the source column. After confirmation and the base animation it
leaves the source and appears in the destination colored before fading to white.
Delete uses a red source treatment before disappearing. On confirmed failure,
restore the prior state with an inverse transition and an actionable error. For
uncertain results retain a distinct pending state until the result is reconciled.

Animate U->C and L->C green with a left-to-right strike-through; C->U blue and
C->L yellow with a right-to-left removal of the strike; U->L yellow; L->U blue;
and confirmed task deletion red. Include deadline edits in either direction,
completion changes, elapsed deadlines while open, multi-task bulk removal, refresh
and remote changes. On startup compare known previous per-account/device status
with synchronized state so tasks that expired while closed can transition without
fabricating a previous state for newly discovered tasks. Also handle moves across
boards and create/delete effects where applicable. Multiple independent cards may
animate concurrently, keeping deterministic per-task sequencing and avoiding
unbounded tickers. Do not force scroll, carousel, board or task position; offscreen
animations still complete. Respect the system's reduced-motion preference and
retain accessible, readable status and the current color palette.
Deadline crossings detected by the local clock do not require an artificial
server write; once known, the base animation completes before the local move.
Preserve the visible scroll anchor through insertions/removals, without fighting
an active gesture, as well as the selected board and Android carousel page.

### Q04 - Visibility of a newly created task while saving

- A. Show it immediately in its destination column as pending, then settle it on
  confirmation; recover its draft if creation is confirmed to have failed
  (recommended: makes the accepted action visible immediately).
- B. Show it only after the server confirms creation; use the sync notice meanwhile.

User answer: A. Show new tasks immediately as pending and confirm after synchronization.

## B04 - Verification and delivery

boundary, startup and refresh, offscreen/scroll retention, rapid independent and
same-task operations, interrupted lifecycle, duplicate submission, optimistic
failure/rollback, unknown outcomes, stale revisions, remote edits, account

verify/install the signed Android APK in place. Run independent tests and builds

results, publish an English PR and do not wait for the remote APK workflow.

## Implementation and delivery status

The user directly requested implementation and answered all four decisions.
The account-scoped encrypted queue, persistent server receipts, conflict handling,
recoverable drafts, immediate form dismissal and coordinated task transitions
are implemented. New writes remain unavailable offline; an unknown network
outcome stays pending and is not blindly replayed against a newer revision.

Validation: 271 Flutter tests and static analysis passed; the TypeScript build
and 15 server tests passed. Automated tests exercise all six column directions,
early and slow confirmation, rollback, clock expiry and startup history, bulk
deletion, account isolation, retry safety, drafts, storage faults and scroll
anchors, plus form behavior when durable local storage is delayed or fails. The
canonical Windows release was rebuilt and reopened; on Windows the
test task was completed and restored. The signed Android release was installed
in place on the Redmi; completion, its inverse, creation, deletion, navigation
and immediate dismissal were checked using the development board. Test records
were removed and the original board/column selections restored. The final
same-task retry guard was additionally checked by automated test and rebuilt.

The backend receipt change will become active in the hosted API after the PR is
merged and the deployment completes. Version 0.9.0 is the next minor after
merged 0.8.0; no major before 1.0.0.
