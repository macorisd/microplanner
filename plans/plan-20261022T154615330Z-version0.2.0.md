# PLAN 0.2.0 — Hosted API, Android APK releases, and matching application icon

## Goal and status

Create a repeatable way to download an installable Android APK from GitHub after
versioned changes, and give Android the same microplanner icon used by Windows.
Host the existing API on Vercel Hobby with the existing MongoDB Atlas database,
so both platforms can connect without the laptop API or USB. Explain the release
concepts and setup so the user can learn the process.

- Baseline: published tag `v0.1.0`, pointing at merged commit
  `a8a5f9eafc09541a537a8ad695f4faa8ee55851b` from PR #2.
- Target: **0.2.0 minor**, following the project's pre-1.0 version policy.
- Status: implementation approved and completed on the feature branch. The API
  is deployed and real device checks have passed. PR delivery and the first
  post-merge tag/APK publication are tracked below. Delivery PR:
  <https://github.com/macorisd/microplanner/pull/3>.
- Proposed implementation branch: `feature/cloud-api-and-android-releases`.
- Three blocks in one plan. B03 hosting and B02 icon precede B01 publication,
  so the published APK uses the reachable API and contains the matching icon.
- Repository text, PRs, release notes, workflow labels, and comments stay English.
  The product name remains lowercase `microplanner`.

## Concepts and recommended direction

| Concept | Meaning | Role for this plan |
|---|---|---|
| Tag | Named reference to a specific commit, such as `v0.2.0` | Identify the exact source version |
| Release | Download page associated with a tag, with notes and attached files | Recommended home for the installable APK |
| Release asset | File attached to a Release | The APK and its checksum |
| Actions workflow | Automated steps run by GitHub | Check, build, sign, and publish the APK |
| Actions artifact | Build output retained for a limited period | Optional intermediate/testing output |
| GitHub Packages | Registries for dependencies/containers such as Maven, npm, or Docker | Not needed for direct APK downloads |

Selected approach: publish a single universal release APK as a Release asset, with a
clear versioned filename such as `microplanner-0.2.0-android.apk`, English release
notes, and a SHA-256 checksum. Use a dedicated persistent signing key and publish
automatically as a prerelease after a successful versioned merge during pre-1.0
development. Automatic publishing is separate from automatic updates
inside the installed app; an in-app updater is outside scope.

### Vercel hosting — feasibility and selected direction

The user asked whether the existing laptop-hosted API could run on Vercel for
free. This is technically feasible: the current Node.js/Fastify backend has an
official Vercel deployment path, and MongoDB Atlas can remain the database.
Windows and Android would call a public HTTPS API instead of the local address,
removing the laptop/USB dependency. The user subsequently accepted Vercel and
requested step-by-step configuration instructions. Hosting is now in scope as
B03. The user subsequently explicitly approved implementing the whole plan.

Vercel Hobby is free for personal, non-commercial use within its quotas. Small
personal/friends usage is a reasonable initial candidate, but capacity must be
verified rather than promised. Exceeding free quotas can pause service. Cold
starts remain possible, and functions have request/response size limits.

B03 covers deployment configuration, runtime initialization and bounded MongoDB
connection reuse, hosted secrets, HTTPS app configuration, and real Windows/
Android checks with the laptop API stopped. Review in-memory rate limiting under
multiple function instances and enforce request/response sizes compatible with
Vercel's 4.5 MB payload limit.

Vercel uses dynamic outbound IPs; the documented basic Atlas connection allows
`0.0.0.0/0`. The user has explicitly confirmed that entry is active and the database
user remains restricted. Preserve authenticated TLS connections and reuse the
existing cluster and data without installing a broader database-role integration.

## B01 — Build and publish Android APKs through GitHub Releases

### Expected behavior

After an approved version is merged and its tag is verified, automation builds
that exact commit, signs an installable APK with a stable identity, and publishes
it with the matching version. The user can find and download it under Releases.
Q03 selects automatic prereleases after successful versioned merges.

### Scope and boundaries

- Extend the existing version-publication flow with explicitly connected build
  and publication steps; keep verified tag/SHA association and immutable tags.
- Build only trusted, merged source. Do not expose signing secrets to untrusted
  PR code or run arbitrary shell content from PR metadata.
- Run appropriate checks before publishing. Failed builds/signing must not
  produce a release claiming an installable APK is available.
- Generate one universal APK initially, plus a checksum and concise English
  notes explaining the intended test/use environment and installation process.
- Verify package, Android versionName/versionCode, signing certificate, and asset
  checksum. Increment Android build numbers so updates can be installed.
- Preserve a stable signing key across CI runners/releases. CI-generated random
  debug keys must not change the app identity from one build to the next.
- Store signing material/passwords in GitHub Actions secrets, never in tracked
  files, build logs, or release assets. Only public API URLs/client IDs go into
  Flutter configuration; MongoDB credentials remain on the API server.
- Register the chosen signing SHA-1 in the existing Google Cloud project so the
  downloaded APK retains working Google login.
- Handle any transition from the currently installed debug-signed app deliberately:
  do not uninstall it or erase its local data automatically. Validate backup/cloud
  data before a signing transition that cannot update it in place.
- Retry publication safely: do not move tags or silently replace a different
  binary already published under an existing immutable version.
- Document the release workflow, downloads, installation, versioning, signing-key
  backup, required configuration, and recovery from a failed publication.
- Google Play, an in-app updater, Windows installers, and paid/custom domains
  remain outside scope. B03 covers API hosting with a Vercel-provided domain.

### Technical integration constraint

The existing tag is created with `GITHUB_TOKEN`. A tag push created by that token
normally does not trigger a second `push: tags` workflow. Connect publishing
explicitly (for example, dependent jobs or an explicit dispatch/reusable flow),
rather than assuming a second workflow will run because a tag was created.
Keep the tag-validation job's checks and minimum necessary permissions.

### Acceptance criteria

1. The selected publication trigger builds the exact verified tagged commit.
2. A successful version has the expected downloadable APK/checksum, correct
   version metadata, and no private configuration bundled in it.
3. Installation and Google sign-in work on the Redmi using the chosen API and
   signing configuration; the existing account's cloud data remain accessible.
4. The Android build contains the Windows-matching icon from B02.
5. Repeated runs are safe and failed checks/signing do not publish misleading
   success. Existing tags and previously released binaries are preserved.
6. Instructions clearly distinguish tag, Release, asset, Actions artifact, and
   package, and describe how to obtain/install the APK and preserve signing keys.
7. The first real publication is verified after the implementation is approved
   and merged, respecting the selected publication policy.

## B03 — Host the existing API on Vercel Hobby

### Expected behavior and scope

Windows and Android call the same stable public HTTPS API on Vercel, using the
existing Google clients and owner-scoped MongoDB data. The laptop API and USB
connection are no longer required for normal use.

- Use a personal Vercel Hobby project connected to `macorisd/microplanner`, with
  Root Directory `server`, Fastify framework, Node.js `24.x`, and production
  branch `main`. The local tested Node version is `24.13.0`.
- Adapt the entry point, runtime startup, and scripts to Vercel's Fastify support.
  The current `src/app.ts` is an app factory, not a listening entry point, and
  local scripts expect `../server.env`; importing main alone does not establish
  a working hosted API. Preserve the existing local development workflow.
- Reuse and bound MongoDB connections per runtime instance, avoid per-request
  initialization/index creation, and recover cleanly from startup failures.
- Review proxy-aware client identification and rate limiting across instances.
  Handle payload limits with clear errors without corrupting stored workspaces.
- Keep the existing Atlas cluster/database, restricted `microplanner_api` user,
  authentication, sessions, account isolation, import receipts, and user data.
- Configure `MONGODB_URI`, `MONGODB_DB=microplanner`, and
  `GOOGLE_WINDOWS_CLIENT_SECRET` privately for Production only. Existing public
  Google client ID defaults remain valid. Local HOST/PORT/DNS overrides are not
  copied to the hosted environment.
- Use Vercel Authentication with Standard Protection: production domain is
  reachable by native clients, while previews remain protected. Production
  database secrets are not assigned to preview builds.
- Explain Atlas dynamic-IP access requirements. The basic free connection uses
  an Atlas `0.0.0.0/0` entry, permitting network connections from any origin while
  still requiring database authentication. The user explicitly configured and
  confirmed it. Do not broaden the database user's role or
  provision a replacement cluster through Marketplace.
- Use a stable Vercel-provided production domain in app build configuration.
  Do not embed secret bypass tokens, database credentials, or OAuth secrets in
  the Windows binary/APK. No custom domain or paid service is required in scope.
- Document deployment, free-plan conditions, environment setup, health checks,
  logs without credentials, rollback, and redeployment after environment changes.
