# microplanner 0.4.0 - Responsive windows and polished Material interactions

## Outcome and hard constraints

Add a native Windows minimum window size, retain colored empty column headers
on Android, fix overlapping sidebar hover feedback, and improve the existing
Material 3 presentation and rendering performance.

Baseline: v0.3.0, merged commit d288577f1d9ab171400e4a903816a4850db0c430.
Target: minor 0.4.0; next Android build number is currently 11.
Proposed branch: feature/responsive-material-interface.

The user explicitly requires preserving current colors. Keep all existing
palette ARGB values, backgrounds, text/button colors, selected/hover colors,
column/priority colors and user-selected subject colors. Wallpaper-derived
colors and generated replacement palettes are excluded. The Android empty
header behavior below is the explicitly requested presentation change.

Preserve authentication, storage, cloud ownership, task rules, compact cards,
visible Android actions, desktop hover actions, Google photo, system bars and
the floating cloud notification. No new dark mode or settings flow is planned.

## Findings and research

- AppTheme already enables Material 3; manually styled surfaces and colors still
  limit its consistent use. Enabling the same flag again is not an improvement.
- Sidebar cards animate their entire decoration for 220 ms, including hover
  exit. Rapid movement can leave a departing hover beside a newly hovered card.
  Interpolation toward transparent black also needs review for dark flashes.
- Empty task columns currently use gray header colors on every platform.
- The Windows runner has no minimum tracking-size policy.
- Workspace notifications propagate through both board and task providers.
  Broad dashboard subscriptions and repeated task filtering/sorting are concrete
  profiling candidates, subsequently measured below.
- Reviewed Cashew commit 9cfbe50c16d95429891d44faf5f2c77a3abdb93b:
  Material/InkWell interactions, controller-driven transitions, selection-scoped
  ValueListenables, responsive sidebar thresholds and Material theme roles.
- Apply those principles through implementations suited to microplanner:
  local interaction state, stable children/identities, appropriate Material
  feedback and responsive constraints. The reference alone cannot establish
  which changes improve microplanner's frame times.

## B01 - Windows minimum size and responsive layout

Set minimum outer window width and height to 50% of the current monitor's width
and height respectively. Use that monitor's physical rectangle, with consistent
DPI handling, rather than a fixed logical size or the combined virtual desktop.

Acceptance criteria:

- Native edge/corner resizing cannot shrink below either half-monitor limit.
- Recompute for monitor, resolution and DPI changes; keep maximize, restore,
  moving and Windows snapping functional.
- At the resulting minimum size, no overflow, clipped controls or unreachable
  dialog actions. Adapt short-height reservations and scrollable forms/pickers.
- Fit three columns where readable; at narrower Windows widths use compact
  navigation and readable columns with an explicit horizontal scroll affordance.
  Retain mouse/keyboard behavior and reachability of the last task.
- Check 1366x768, 1920x1080 and 2560x1440 calculations at 100/125/150/200% scaling.
  Distinguish simulated cases from actual hardware checks.

Decision: use the user's explicit half-screen rule. Adapt the interface rather
than introducing an additional larger fixed minimum.

<!-- md-block {"id":"B02","dependsOn":[]} -->
## B02 - Platform-specific empty column headers

Android always uses each column's existing semantic header foreground and
background: Complete, Late and Upcoming, including at zero tasks. Windows keeps
its gray empty headers.

Acceptance criteria:

- Cover empty/populated columns on Android and Windows independently of width.
- Title, icon and count remain readable with the unchanged semantic colors.
- Completing/removing the last task reaches the correct platform state without
  a flash or incorrect intermediate color.

Decision: explicitly specified by the user; no further design choice is needed.

<!-- md-block {"id":"B03","dependsOn":[]} -->
## B03 - Immediate, exclusive sidebar hover feedback

Separate pointer feedback from selected-board styling. Clear departing hover
immediately so only the item under the pointer can display its hover background.
Any entrance/selection motion stays bounded and interruptible.

Acceptance criteria:

- Rapid jumps never leave hover backgrounds on two unselected cards, including
  the next animation frame; no dark flash from transparent-black interpolation.
- Selected styling, keyboard focus, nested Subjects/actions and rename remain
  usable. Windows action reveal and persistent Android touch actions are retained.
- Pointer changes rebuild only the affected local interaction surfaces.
- Verify reversals, pointer exit, board switch, rename and drawer changes.

Decision: delayed exit trails are a visual regression, not intended motion.

<!-- md-block {"id":"B04","dependsOn":["B03"]} -->
## B04 - Measure and reduce rendering/rebuild work

Capture a repeatable baseline before optimization and repeat identical
interactions afterward on the same hardware/build mode. Separate UI-thread,
raster-thread and cloud-request time.

Investigate narrow subscriptions and duplicate invalidations; repeated task
group/subject lookup work; animation builders and large nested fade/scale/layout
work; expensive paints; and repeated immutable theme/font configuration.
Choose changes based on evidence. Cache invalidation must cover account, board,
data, deadline/time and resume, including correct clock-sensitive task states.

Acceptance criteria:

- Measure board switching, rapid hover, task scrolling, dialog open/close and
  task transitions using appropriate profile/release runs.
- Record UI/raster frame-time distributions and over-budget frames where tracing
  is supported, using the actual refresh interval without forcing 60 Hz.
- Compare warm equivalent runs and report results/limitations honestly. Static
  screenshots alone do not establish performance.
- Demonstrate targeted rebuild/render reductions and avoid consistent regression
  in other tested interaction paths.
- Animations never delay input handlers, duplicate writes or show failed or
  unconfirmed cloud writes as saved. Preserve account isolation, late-response
  rejection, task ordering, scroll positions and reduced-motion behavior.
- Diagnostic output contains aggregate timing data and synthetic identifiers,
  not credentials or personal planner contents.

## B05 - Material 3 polish with the exact existing palette

Improve shared component geometry, typographic hierarchy, Material roles,
focus/press feedback and appropriate elevation across the existing interface.

Acceptance criteria:

- Do not change palette ARGB values or introduce a new accent, seed-generated
  replacement palette, wallpaper colors or automatic color personalization.
- Preserve existing background/foreground colors; map any additional Material
  roles to existing palette values.
- Retain compact tasks, text-sized subject badges, Android edit without
  automatic keyboard, 48 dp touch targets and desktop keyboard/hover usability.
- Cancel/delete controls retain their existing red treatment. Preserve the
  icon/avatar and Android system-bar integration.
- Coordinate shapes, sizes and state feedback without adding idle animation.

Decision: Material 3 is already enabled. The user's clarification makes color
preservation a hard constraint on all visual changes.

## Implementation and approval

The user approved implementation of all six blocks. The branch is
`feature/responsive-material-interface`; approval did not authorize merging.

- B01: native minimum tracking dimensions use half the current physical monitor
  rectangle, rounded up for odd dimensions. Recheck after moves, display changes
  and DPI changes. Narrow desktop layouts use compact navigation and an explicit
  horizontal scrollbar; short layouts reduce reservations and keep forms and
  date/time pickers scrollable. Very narrow desktop calendars use date input.
- B02: Android retains each column's existing semantic colors when empty;
  Windows retains the gray empty state.
- B03: board hover decoration updates immediately, independently of selection
  and keyboard focus. Removed the departing background color tween. Pointer
  movement only changes the corresponding card's local interaction state.
- B04: cached immutable board/subject indexes and task groups, semantic change
  detection, per-column selectors, subject-specific card subscriptions, stable
  hover children and cached formatters/theme. Status-only refreshes no longer
  invalidate tasks. Clock boundaries, backward clock changes and account changes
  invalidate derived views. Columns translate without whole-list opacity;
  dialogs use a small opaque slide with a separately animated modal barrier.
- B05: additional Material 3 roles use existing palette values; coordinated
  menu/icon shapes and dialog elevation. `app_colors.dart` is unchanged. Retained
  original card shadows, spacing, touch targets and platform action behavior.
- B06: manifests synchronized to 0.4.0, Android build 11. Local release builds,
  device verification and publication evidence are recorded below.

## Performance evidence

Compared release-engine frame timings against v0.3.0 on the same Windows PC and
Redmi. A private, memory-only harness used 180 synthetic tasks across three
boards, repeated six interaction phases, and compared the second (warm) run.
Diagnostics did not read or write the user's cloud data or credentials and are
excluded from the application and repository.

Warm-run p95 timings in milliseconds (UI / raster, baseline -> final):

| Interaction | Windows | Android |
| --- | --- | --- |
| Board switch | 27.91 / 4.91 -> 26.81 / 5.11 | 4.79 / 16.20 -> 3.44 / 13.88 |
| Subject navigation | 13.34 / 4.83 -> 2.99 / 2.82 | 11.95 / 3.60 -> 3.92 / 7.64 |
| Dialog open/close | 4.01 / 5.43 -> 1.82 / 2.70 | 7.04 / 24.57 -> 8.40 / 16.27 |
| Task scrolling | 5.79 / 4.82 -> 3.45 / 2.79 | 3.35 / 13.63 -> 9.71 / 9.80 |
| Task state change | 18.22 / 4.19 -> 6.81 / 2.72 | 14.67 / 14.41 -> 12.55 / 12.35 |
| Cloud status refresh | 15.73 / 2.72 -> 1.08 / 2.21 | 16.48 / 3.00 -> 5.28 / 5.53 |

Eight confirmed task mutations produced 32 task notifications before and eight
after. Eight status refreshes produced 32 before and zero after; subject-only
navigation produced eight before and zero after. These are structural reductions,
not measurements of network latency. Android's closed drawer does not animate
during the subject phase, so its eight-frame percentile is particularly noisy.

The Redmi reported 120 Hz (8.33 ms budget). Board-switch over-budget frames fell
from 155/202 to 48/203; task-state frames from 50/185 to 37/177. Dialogs still
exceeded that budget on 142/151 frames, and scrolling on 37/261. Android scrolling
UI p95 increased although raster p95 decreased; not every timing improved. These
single-device warm runs include scheduling/thermal variation and do not establish
constant 60 or 120 fps. Windows did not expose refresh rate through this Flutter
engine API, so no Windows over-budget count is claimed. An alternative card-shadow
implementation and staged mounting were discarded after unfavorable measurements;
the final version retains the original card shadows and direct mounting.
