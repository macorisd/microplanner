## Existing system and constraints

- Flutter already targets Android and Windows. There is no notification plugin,
  OS permission flow, background reminder service or notification preferences.
- Tasks have an exact deadline, completion flag, stable ID and board ID. There is
  no date-only deadline: the creation form currently defaults its time to 23:55.
  Keep that behavior. Snapshot JSON stores UTC instants and converts to local
  time for display; do not reinterpret deadlines when the time zone changes.
- The account-scoped cloud workspace uses revision checks, encrypted local cache
  and an outbox. Its visible snapshot can contain pending creations. Scheduling
  must distinguish confirmed data from optimistic state and unresolved writes.
- Settings currently has a linear Customization navigation path. Notifications
  adds a sibling destination, requiring explicit route history rather than
  assuming every Back action means the previous numeric page.
- Windows normally runs the unpackaged bundle at
  `build/windows/x64/runner/Release/microplanner.exe`; closing its window currently
  exits the process. Preserve this launch target and close behavior.
- Apply the existing [visual](../decisions/visual-design.md),
  [interaction/data](../decisions/interaction-and-data.md),
  [verification](../decisions/verification.md) and
  [delivery](../decisions/delivery.md) contracts. This request explicitly extends
  the former Settings-only-Customization scope; it does not remove Customization.

## B01 - Reminder behavior and delivery boundary

**Objective:** deliver useful reminders without repeatedly interrupting the user.

### Proposed behavior

1. Include incomplete tasks on every board, independent of the selected board.
   The default advance reminder is **24 hours before the deadline**.
2. Permit one advance reminder per task and an optional second reminder at the
   deadline, disabled by default. No repeating overdue reminders or priority-based
   escalation. Never manufacture historical reminders for already overdue tasks.
3. A task uses the current account default unless explicitly disabled or given
   its own advance time. Changes to the default update inheriting tasks, including
   existing tasks, while preserving overrides.
4. If enabling reminders, creating a task or changing its deadline places its
   advance reminder in the past but the deadline is still ahead, issue one
   immediate reminder. A repeated refresh, restart or settings save must not
   repeat it. Enabling the optional deadline reminder adds a distinct event.
5. Batch simultaneous immediate reminders into one summary rather than a burst.
   A single reminder shows task title, board and the exact local deadline; omit
   description text. A summary shows the task count. System notification grouping
   should keep multiple ordinary reminders together where supported.
6. Clicking a single reminder opens the correct account's board and reveals the
   task without editing or completing it. A summary opens the earliest still
   eligible task from its batch. Resolve against current data after startup/login.
   If the task disappeared, show a short unavailable message. Never open another
   account's task or replace an unsaved draft; defer navigation until it is safe.
7. Completion, deletion, board deletion or disabling reminders cancels affected
   future events. Deadline/override edits replace the old schedule. On receipt
   of a confirmed cloud change, reconcile both future and displayed reminders
   where the platform supports removal. Dismissing a notification changes no task.

### Honest delivery limits

- Use **local OS-scheduled reminders**, so already scheduled events can work
  offline and with the app closed. Scheduling is based on the last synchronized
  workspace. An edit on the other device is not known until this device syncs;
  stale reminders can therefore occur while it stays closed or offline.
- Android and Windows each notify if enabled there. Prevent duplicates within a
  device, not across devices. No push server, continuous background cloud polling,
  tray process, autostart or always-running service is included in this release.
- Delivery is subject to device power, OS notification settings, Android battery
  management and scheduling permissions. Do not promise an alarm-clock guarantee.
  On reopen/resume, reconcile missed events once for still-upcoming tasks; do not
  replay reminders for tasks that are already late or completed.
- Preserve the current deadline instant across time-zone/DST changes. A 24-hour
  advance means an elapsed 24 hours; quiet hours use the device's local clock.

**Acceptance:** fixed-clock scenarios cover before/at/after the reminder and
deadline, all boards, disabled/completed tasks, batch catch-up and repeated
restart/refresh without duplicate events. Device verification must distinguish
normal app closure from Android Force stop and a powered-off computer.

**Questions/answers:** no separate answer required; these are proposed rules for
the complete-plan approval. No user approval has been recorded.

## B02 - Settings > Notifications and task overrides

**Objective:** make reminder timing and device readiness understandable in one place.

Add Notifications beside Customization in Settings. Preserve the existing
Customization subtree, Profile contents, Back/Escape behavior and last board.
Use explicit destinations/history for this new branch. Match the existing
480-pixel account panel, colors, spacing, selectors and accessible targets.

| Control | Proposed default and behavior | Storage scope |
| --- | --- | --- |
| Enable notifications on this device | Off until enabled; requests OS access in context. Disabling cancels this account's scheduled events here. | Account + device |
| Default reminder | 24 hours before; presets 15 minutes, 30 minutes, 1 hour, 3 hours, 1 day, 2 days, 1 week, plus Custom. Custom accepts 1-10,080 whole minutes with minute/hour/day input. | Account, synchronized |
| Also remind at the deadline | Off; adds one event except for tasks with reminders disabled. | Account, synchronized |
| Quiet hours | Off; when enabled suggest 22:00-08:00, editable. Support overnight intervals; reject identical start/end. | Account + device |
| Show task details | On; Off uses generic text and hides task/board/deadline content in all generated notifications. | Account + device |
| Delivery status | Enabled, disabled, permission blocked, timing may be delayed, setup failed or partly scheduled; show useful next action. | Read from OS + local scheduler |
| Open system notification settings | Manage sound, vibration, banners, lock-screen display and OS Do Not Disturb there. Avoid a competing app sound switch. | OS |
| Send test notification | One harmless sample, no cloud task creation; unavailable until notification permission is granted. | Device action |

Quiet hours delay an advance reminder to the next allowed local time **only if
that time is before its deadline**; otherwise skip that event. A deadline reminder
inside quiet hours is skipped. Never override OS Do Not Disturb or notify after
quiet hours about a task that has become late. The test action is explicit and
can run during app quiet hours; explain this beside the action. Quiet-hour edits
recalculate pending events without resetting already-issued event identities.

Use immediate persistence for page toggles/selectors, with concise failure and
pending feedback and rollback on definite failure. Local device preferences can
change offline. Cloud preferences follow the existing online editing/outbox
rules. Custom timing uses the shared validated edit dialog, fixed white footer,
red Cancel and Save changes; unchanged/invalid values cannot save. Returning from
system settings refreshes status without losing the current page.

Add a compact **Reminder** selector after Deadline/Time in New/Edit Task:
Use default (show its current value), No reminder, or Custom advance time using
the same presets/validation. The account's optional deadline event applies to
both inherited/custom reminders, and No reminder suppresses both. Preserve
Subject > Task type > Deadline/Time order, focus, description, keyboard and pickers.
An override is saved with the task, not by changing the account default. Existing
tasks inherit automatically; do not rewrite every task on activation.

**Acceptance:** navigation unwinds correctly from both Settings branches; current
values/scope are clear; denied access is not shown as working; local and cloud
save failures preserve the accepted data rules. Check compact Windows, portrait
Android, enlarged text, keyboard, custom-duration errors and offline states.

## B03 - Shared preferences, reconciliation and data compatibility

**Objective:** keep notifications consistent with confirmed tasks and account safety.

### Model and persistence

- Add account notification defaults and a task reminder policy with explicit
  inherit/off/custom semantics. Missing fields mean inherit and the defaults
  above. Device enablement, privacy, quiet hours and OS permission are not cloud
  preferences; never enable a second device because the first was enabled.
- Extend snapshot serialization/cloning, delta comparison/rebase, outbox drafts,
  API validation and repository persistence together. Choose an additive versioned
  representation and deploy the compatible API before updated clients.
- Older full-workspace clients must not erase new preferences/overrides. Detect
  omitted fields and retain stored values for existing IDs; explicit reset to
  inherit must remain distinguishable from omission. Test mixed-version edits,
  imports, retries and revision conflicts. Never relax account isolation.
- Store device settings and scheduling ledger with the existing protected,
  account-scoped storage. OS payloads contain only necessary opaque routing IDs
  and configured display text, never session tokens or task descriptions.

### Scheduling engine

- Provide a shared pure reminder planner and platform adapters for availability,
  schedule, remove pending, remove displayed, test and activation handling.
  Keep failures separate from cloud-save success; a failed OS schedule must be
  visible and retryable without repeating a task write.
- Maintain a durable mapping from account/task/deadline/reminder-kind to OS IDs
  and a schedule fingerprint. Use deterministic collision-safe identifiers and
  serialized reconciliation with generation checks on account/lifecycle changes.
  Title, privacy or preference edits must not reissue an event already submitted
  for the same task/deadline/kind. A new deadline is a new occurrence.
- Reconcile at login/restore, confirmed writes, refresh/resume, settings changes,
  clock/time-zone changes and applicable OS boot/update events. Debounce changes;
  do not introduce frequent Dart polling or UI rebuilds to detect deadlines.
- Schedule new/edited events from confirmed data. For an accepted pending
  completion/delete/deadline or reminder edit, suppress the old future events
  immediately; after confirmation rebuild from the accepted state. Definite
  failure restores the confirmed schedule once. An unknown write outcome remains
  suppressed until resolved, preventing an obsolete reminder during a slow save.
- On sign-out/account replacement, cancel prior-account events before enabling
  another schedule; clear displayed content where supported and reject stale
  async callbacks and launch payloads. Handle app-detected expiry the same way.
  An OS-only scheduled event cannot observe a server-side logout while closed;
  document this boundary and bound scheduling to the locally known session expiry.
- Treat the ledger as scheduling/submission evidence, not proof the user saw an
  OS banner. Do not promise exactly-once display across an OS crash. Reconciliation
  favors no repeated catch-up after an ambiguous delivery.
- Bound resource use: schedule the nearest **200 individual reminder events**
  initially, or fewer if the verified adapter limit requires it, ordered by time.
  Refill on reconciliation; schedule across all future dates without a separate
  time horizon. If eligible events exceed capacity or session expiry, show partial
  coverage/count and explain that reopening/synchronizing replenishes the queue.
  Never silently claim all tasks are covered. No duplicate pending OS IDs.

**Acceptance:** planner/controller tests cover quiet-hour midnight/DST boundaries,
overrides/default changes, capacity, privacy, crash restoration, slow/failed and
unknown writes, completion undo, logout/account switches and out-of-order results.
API tests prove backward compatibility and account isolation using isolated data.

**Questions/answers:** technical representation is an implementation choice within
this contract; changes to the user-visible behavior require plan revision.

## B04 - Android delivery and permissions

**Objective:** reminders are owned by Android, not an open Flutter screen.

- Prefer a compatible stable `flutter_local_notifications` release for Android,
  plus timezone support where required. Pin compatible dependencies after checking
  the installed Flutter/Dart/Gradle toolchain; do not upgrade unrelated packages.
- Configure a monochrome notification icon, reminder channel, runtime notification
  permission where required, scheduling receivers and boot/app-update restoration.
  Preserve the package, signing identity, portrait lock and normal startup.
- Request notification access only after the user enables the feature. Offer
  precise reminder access with a short explanation when required; use
  `SCHEDULE_EXACT_ALARM` rather than assuming restricted `USE_EXACT_ALARM` access.
  If precise access is declined/revoked, fall back to permitted inexact scheduling
  and visibly report that reminders may be delayed. No repeated permission prompts.
- Respect OS channel settings. Report notification denial separately from timing
  restrictions. Link to the appropriate app/system settings and reevaluate on return.
- Rebuild schedules after reboot/update using only the active account's protected
  schedule metadata and known session expiry. A thin native receiver/guard may be
  needed if the plugin cannot suppress expired or signed-out events before display;
  validate this instead of assuming a Dart callback always runs in the background.
- Handle launch from foreground/background/terminated app once. A stale payload
  cannot bypass login, resurrect a deleted task or open duplicate editors.
- Test Doze, ordinary removal from recents and actual Redmi battery behavior.
  Force stop, hibernation and vendor restrictions can suspend delivery; reopening
  repairs the schedule. Provide specific help only when relevant, without silently
  changing the phone's battery or notification settings.

**Acceptance:** a scheduled notification arrives with Flutter closed and opens
the right task; completion/rescheduling cancels the old event; denial, inexact
fallback, privacy, restart restoration and account switching behave as specified.
Record actual timing and any device restriction rather than claiming guaranteed
precision. Ask for physical phone connection/unlock early during implementation.

**Questions/answers:** no physical-device action is needed for this planning task.

## B05 - Windows delivery from the normal unpackaged bundle

**Objective:** Windows shows and opens scheduled reminders even after normal exit.

### Early feasibility gate after approval

Before broad settings/data work, validate a minimal Windows adapter against the
normal release executable: schedule, enumerate/remove a pending event, close
the app, receive a notification, click it, and remove displayed notifications.
Use a fake reminder through the adapter for this gate, not personal task edits.
The integration gate may be developed against a small interface before B03 is
fully integrated; final B05 completion depends on B03.

The usual Flutter Windows plugin documents cancellation/history limitations for
apps without package identity. Do not assume a generic cross-platform API solves
the existing EXE distribution. Microsoft provides local notification registration
for unpackaged desktop apps and OS scheduling APIs, but this exact combination
must be proven on the installed bundle.

### Proposed integration

- Prefer a Windows-specific native adapter using the supported Windows notification
  APIs, stable microplanner app identity and user-scoped activation registration.
  Use WinRT scheduling/cancellation and an appropriate COM activation path; assess
  deployment/runtime requirements in the gate. Reuse a plugin only if it passes
  the same unpackaged tests and supplies the required behavior.
- Preserve the canonical EXE and full bundle. Any required Start Menu registration
  points to it; do not repoint the taskbar shortcut or require a replacement MSIX,
  administrator privileges, scheduled PowerShell commands or a resident helper.
- Handle cold activation and an already-running instance without launching a
  second workspace or stealing an unsaved draft. Keep the ordinary close-to-exit
  behavior; OS ownership of scheduled events supplies closed-app reminders.
- Distinguish removing pending schedules from clearing notification-center
  history. Do not claim cancellation works because an API call returns success;
  verify that the old reminder never fires and the displayed entry is removed.
- Respect Windows notifications/Do Not Disturb; show setup/availability failures.
  A sleeping/offline computer may miss the OS delivery window. Reconcile on next
  launch/resume as B01 defines, without guaranteeing a wakeup or replaying late tasks.
- If a mandatory capability cannot be provided for this bundle, pause the affected
  integration and present the concrete revised choices before changing packaging
  or reducing behavior. Do not silently deliver an open-app-only implementation.

**Acceptance:** demonstrate real scheduled delivery after process exit, cancellation
before delivery, click-to-open for cold/warm launches, identity/icon, notification
center cleanup, disabled OS notifications, reboot/resume and no second instance.
Record the gate outcome before committing to the final adapter/dependencies.

**Questions/answers:** feasibility is not yet experimentally verified; no packaging
change or background process is proposed for approval.
