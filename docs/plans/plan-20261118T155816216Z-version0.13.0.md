# Permanent account deletion in microplanner 0.13.0

## Status and scope

Approved for implementation on 2026-11-18. The user requested a minor release that
lets someone permanently delete their microplanner account and all associated
data from Settings > Account. The user explicitly prohibited deletion testing
with their account. The latest remote release at planning time is v0.12.0.
Recheck the release base and use the updated main branch when starting work.

The confirmation and cleanup details below are proposed implementation choices.
Apply the existing [visual design](../decisions/visual-design.md),
[interaction and data](../decisions/interaction-and-data.md),
[verification](../decisions/verification.md) and [delivery](../decisions/delivery.md)
contracts. The feature concerns data held by microplanner. The Google account
continues to exist. A later deliberate sign-in may create a fresh microplanner
account with a new identity and an empty workspace with its standard first board.

## B01 - Permanently erase the cloud account

Add a destructive API operation for the authenticated account. Reuse Google
identity verification with a fresh, short-lived, one-time deletion authorization
bound to the current session and account. Require the same verified Google
subject and confirm the active account inside the deletion boundary. A request
body cannot target another account. Keep the reauthentication flow separate from
ordinary sign-in and account creation.

Inventory and hard-delete all account-owned data in one MongoDB transaction.
Include the profile and Google identity link, all sessions, boards, tasks,
subjects, board task types, reusable type lists, synced preferences and reminder
settings, operation receipts and legacy import receipts. Include any additional
account-owned data found during implementation. Revoke all sessions at commit.
Coordinate deletion with concurrent saves, imports and session issuance so an
in-flight request cannot recreate records for the deleted identity.

Cover failed transactions, repeated submissions and a committed deletion whose
response is lost. Use a short-lived, scoped way to verify the outcome during
recovery, with no personal data or saved workspace, and purge any temporary
verification state. Keep tokens, account details and user content out of logs.
A normal expired session alone must be insufficient to infer account deletion.

Before exposing the action, inventory deployed Atlas backups, snapshots, logs
and any other copies controlled by microplanner. Verify actual retention,
supported erasure and restore behavior. Document how deleted records are kept
out of restored service and resolve any retained recoverable copy with the user
if the deployment cannot delete it immediately. Record verified limits before
promising permanent erasure. The app cannot remove copies separately kept by
users or third parties.

Acceptance criteria include zero remaining account-owned live records, all old
sessions rejected, another account's data preserved, no partial deletion on
failure and no resurrection by concurrent or retried requests.

## B02 - Confirm deletion from Settings > Account

Place **Delete account** below the account actions on Windows and Android.
Display the account being deleted and state that its data, including unsynced
changes, will be permanently lost. Explain what happens on other devices when
they reconnect. Use the shared deletion dialog and fixed footer with **Cancel**
and **Delete**, clear destructive styling and safe keyboard focus. Preserve the
existing Settings navigation and sign-out behavior.

Require a connection and fresh Google verification. Show the account and obtain
an explicit final confirmation before submitting. Cancel, Back, or a dismissed
or mismatched Google account leaves data intact. After submission, prevent
duplicate requests and distinguish a confirmed failure from an unknown result.
For a lost response, show verification and recovery status without inviting a
second independent deletion. Announce progress and errors accessibly. Return
to the signed-out screen after confirmed deletion and safe local teardown.

Acceptance criteria cover accidental activation, keyboard and Back behavior,
correct account identification, verification cancellation, offline use, pending
state, errors and success across both platforms.

## B03 - Remove device data and stop reminders

Once deletion is confirmed, close the deleted account's workspace and stop any
foreground or background work that could read or rewrite it. Remove its secure
credentials, encrypted Hive workspace and key, outbox, failed actions and
drafts, board and column selections, reminder preferences, cached snapshots,
ledger and sync state. Cancel its scheduled and displayed OS reminders where
supported and invalidate its callbacks. Make cleanup repeatable after interruption
and prevent a late write or OS callback from repopulating deleted state.

Inspect legacy Hive data and its import markers. Remove copies attributable to
the deleted account and block their reimport. Preserve data owned by another
account or whose ownership is unknown. If legacy ownership cannot be resolved,
record the limit before claiming complete local erasure.

All other devices lose cloud access at commit. On the next successful contact,
a compatible client must recognize verified deletion, stop the deleted
workspace and purge its local data and reminders. Plan the signal so that normal
session expiry and sign-out retain their existing semantics. Account for prior
clients and offline devices explicitly. An offline or outdated device may retain
cached data and already scheduled reminders until it runs compatible cleanup
online or its local account data is cleared. State that limit in the product
flow and verification evidence.

Acceptance criteria include successful and interrupted cleanup, no replay of
pending mutations, no resurrection from legacy import, stale notification taps
being rejected, and no cross-account cache or reminder removal.

## B04 - Verify without deleting the user's account

- Exercise API deletion against an isolated replica set with two synthetic users
  and identifiable records in every affected store. Verify atomic rollback,
  authorization and account isolation, concurrent save/import/sign-in, session
  invalidation, duplicate submission, lost response and a fresh account after
  deliberate sign-in.
- Exercise client state transitions with isolated fixtures, including cancellation,
  reauthentication mismatch, pending changes, network loss, crash recovery,
  cache cleanup and a second device reconnecting. Cover legacy account attribution
  and stale reminders or queued writes.
- Perform real Windows computer use and physical Android ADB verification.
  Exercise the destructive path only with explicitly identified disposable
  accounts and separate test data, preferably through an isolated backend.
  Confirm test identities and endpoint before submitting. Use the normal
  installations only for safe UI inspection up to the confirmation boundary
  while the user is signed in. Keep the user's account, data and session intact.
  Prueba Desarrollo is part of the user's account and cannot isolate deletion.
- Run Flutter analysis and tests and server build and tests. Record real evidence,
  including offline and older-device limits. For delivery, verify the compatible
  API before offering the client action, use the canonical Windows build and
  signed Android update, and follow the project release workflow.

## Implementation and verification

- The deletion grant expires in five minutes and is valid only for the session
  that verified the same Google identity. The transaction removes the grant
  alongside the account and its records. A read-only signed account-status
  proof lets an enrolled client confirm deletion after session revocation
  without a retained server account or tombstone. A protected local journal
  lets cleanup resume after a lost response or restart.
- Windows and Android verified on the normal installations with the user's
  session retained. Opened the warning dialog from Settings > Account and
  dismissed it with Escape or Android Back. The final destructive action was
  exercised only in isolated automated cases. Live Google reauthentication
  with a disposable Google account was outside this device verification.
- Flutter analysis passed, with 559 Flutter tests and 27 API tests passing.
  Release safeguard tests passed (38 tests). The canonical Windows build and
  the persistent-signature Android update both report 0.13.0+33. The Windows
  interaction was captured at normal size. The connector could not resize the
  window, so the 768 by 456 compact layout was covered by the widget test.
- Atlas showed the free microplanner cluster with backups disabled and no
  recoverable snapshots in its Backup area. The production key is configured
  as a Vercel secret. Deployment smoke checks must use anonymous requests or
  dedicated test fixtures and must never submit deletion for the user's account.
  Existing copies held by users, unattributed legacy device data and old
  devices without a compatible status proof are outside remote erasure.
